# Shop Counter: tool contract (v1.7.1, 2026-10-13)

Single source of truth between the MCP server (`apps/shop-counter`, `packages/shelf`) and the Echo Show simulator (`apps/echo-sim`). Change it here first.

## Transport
- MCP spec 2025-11-25, Streamable HTTP, endpoint `POST /mcp`, stateless (no `Mcp-Session-Id`). `/mcp` serves the default store (Satechi); every store is also at `POST /stores/<id>/mcp` (`satechi`, `roborock`). `GET /health` lists them.
- Shopper identity: `Authorization: Bearer <session>`, an HMAC-signed session from `POST /auth/demo-login {"profile":"maya"|"sam"|"guest"}` -> `{token, user_id, profile, expires_at}` (24 h; `guest` = a fresh private id). The server takes the shopper id ONLY from a valid session. No `Authorization` -> `anonymous` (no memory, no orders). A forged, foreign-secret, expired, malformed or wrong-audience token -> HTTP 401 with `WWW-Authenticate: Bearer error="invalid_token", error_description="...", resource_metadata="<origin>/.well-known/oauth-protected-resource<path>", scope="shopper"`, nothing runs. A bare `x-user-id` header is ignored unless the local dev flag `SHOP_COUNTER_DEV_USER_HEADER=1` is set (never on Lambda). The same Bearer slot also takes an OAuth access token from account linking (section Auth); the demo login stays as the fallback.
- Memory scope: the device closet (`remember_my_devices`, `my_devices`) belongs to the shopper and is shared by every store; orders, tickets and confirmations are per store.
- Every tool result = `content[0].text` (one or two short sentences, enforced in code: longer lines are cut between sentences; written to be SPOKEN by Alexa, no URLs, no SKUs) + `structuredContent` (below) + `_meta.ui.resourceUri = "ui://shop-counter/view.html"` for tools marked [UI].
- Facts (price, availability, compatibility) come only from the store feed. Never invented. Unknown -> say unknown.

## Auth: account linking (v1.7)
OAuth 2.1 after the MCP Authorization spec 2025-11-25, built into the same server (`apps/shop-counter/src/oauth.ts`). `<origin>` = `PUBLIC_BASE_URL`, else the Lambda Function URL host (https), else the request Host (http, local).
- Protected Resource Metadata (RFC 9728): `GET /.well-known/oauth-protected-resource` (resource = `<origin>`, the whole server, every store), `/.well-known/oauth-protected-resource/mcp` and `/.well-known/oauth-protected-resource/stores/<id>/mcp` (resource = that endpoint). Fields: `resource`, `authorization_servers: [<origin>]`, `scopes_supported: ["shopper"]`, `bearer_methods_supported: ["header"]`, `resource_name`.
- Authorization Server Metadata (RFC 8414): `GET /.well-known/oauth-authorization-server` -> `issuer`, `authorization_endpoint` (`/authorize`), `token_endpoint` (`/token`), `registration_endpoint` (`/register`), `code_challenge_methods_supported: ["S256"]`, `grant_types_supported: ["authorization_code","refresh_token"]`, `token_endpoint_auth_methods_supported: ["none"]`, `client_id_metadata_document_supported: true`, `authorization_response_iss_parameter_supported: true`.
- Clients (public only, no client secrets): (1) Client ID Metadata Document: `client_id` is an https URL with a path; the server fetches it (3 s, 5 KB, no redirects, no IP-literal or local hosts, cached 5 min), requires `client_id` equal to the URL, `client_name`, `redirect_uris` (https or localhost). (2) Dynamic Client Registration (RFC 7591): `POST /register {client_name, redirect_uris[1..5]}` -> 201 `{client_id, client_name, redirect_uris, token_endpoint_auth_method:"none", ...}`. The `client_id` is the signed registration itself (`dcr.<payload>.<hmac>`), nothing is stored.
- `GET /authorize`: `response_type=code`, `client_id`, `redirect_uri` (exact match with the registered list; may be omitted when only one is registered), `code_challenge` + `code_challenge_method=S256` (required, `plain` refused), `state`, `scope` (only `shopper`), `resource` (RFC 8707; must be `<origin>` or one of our MCP endpoints; absent -> `<origin>`). An unknown client or unregistered `redirect_uri` -> an HTML error page (400), never a redirect. Other errors -> redirect with `error` (`invalid_request`, `invalid_target`, `invalid_scope`, `unsupported_response_type`), `state`, `iss`. A valid request -> the consent page "Link Shop Counter to Alexa": the client name, the redirect host (flagged when it is localhost), the stores covered, a choice of shopper (Maya, Sam, new guest), Allow / Cancel. `POST /authorize` (form) re-checks everything; Allow -> 302 to `redirect_uri?code&state&iss`, Cancel -> `error=access_denied`.
- Code: HMAC-signed, 60 s, bound to client, redirect_uri, PKCE challenge, resource, shopper, scope. One-time: spent in the state store under `oauth-used:<shopper>` (DynamoDB conditional put on Lambda), only after every other check passed.
- `POST /token` (form or JSON, `cache-control: no-store`): `grant_type=authorization_code` needs `client_id`, `code`, `redirect_uri`, `code_verifier` (43-128 chars, SHA-256 must match), optional `resource` (must equal the authorized one). `grant_type=refresh_token` needs `client_id`, `refresh_token`, optional `resource` (same or narrower: whole server -> one store). Response `{access_token, token_type:"Bearer", expires_in:3600, refresh_token, scope:"shopper", resource, user_id}`. Refresh tokens: 30 days, rotated, each one usable once. Errors: 400 `invalid_grant` (unknown, expired, used, wrong client, wrong redirect_uri, PKCE mismatch), `invalid_target`, `unsupported_grant_type`; 401 `invalid_client` when an `Authorization` header is sent (public clients only).
- Access token = the shop's signed session with an audience `a` (1 h). At an MCP endpoint it is accepted when `a` is `<origin>` or exactly `<origin><path>`; any other audience -> 401 `invalid_token` ("token was issued for another resource"). Demo-login sessions carry no audience and work at every store, as before.
- No token: still `anonymous` (search, compare and compatibility work; closet and order tools return error `anonymous`). Opt-in `SHOP_COUNTER_REQUIRE_AUTH=1` answers 401 with `WWW-Authenticate: Bearer resource_metadata="...", scope="shopper"` instead, for clients that discover auth only through a 401.

## Product object
```json
{ "id": "string (variant-stable id)", "handle": "string", "title": "string", "vendor": "string",
  "variant": "Silver | US | null (option value of this variant; null for single-variant products)",
  "price": 49.99, "currency": "USD", "compare_at_price": 59.99, "available": true,
  "image": "https://... | null", "url": "https://store/products/handle?variant=id",
  "highlights": ["100W USB-C PD", "3 ports"], "compatible_with": ["iPhone 15", "MacBook Air M2"],
  "why": ["Fits your iPhone 15 (store lists it)", "Under your $60 budget"] }
```

## Tools
1. `find_products` [UI] input `{ need: string, max_price?: number, category?: string, must_have?: string[], for_devices?: string[] }`. Uses the shopper's device closet only when neither `for_devices` nor the need names a device: a device in the request wins ("a charger for my Pixel" is about the Pixel, never the iPhone on file). A bare family name ("Pixel", "Galaxy", "iPhone") cannot be checked, so the spoken text asks for the model. "The store lists it for your X" is said only when the store lists X by its exact model; a series-only listing is said as "The store lists it for iPhone 17, not your iPhone 17 Pro specifically". Returns `{ kind:"products", store, need, for_devices: string[], max_price: number|null, products: Product[<=3], more_available: number, out_of_stock_match: Product|null }`. `max_price` may come from the need text ("under $50"). Empty `products` is a normal answer (the spoken text says why: nothing matched, over budget, out of stock, a wattage nobody has, or a brand/model the store does not sell). Protection plans, trade-in offers and points items are returned only when the need asks for them. When the shopper names a brand/model the store does not sell or a product that is out of stock, the spoken text says so first, then names the closest real option. That holds with `for_devices` too (a named product the store does not list for the device). The named out-of-stock product itself is `out_of_stock_match` (`available: false`): never offered or orderable, but its id works in `check_compatibility`, so "will it fit?" still gets the store's answer.
2. `compare_products` [UI] input `{ ids: string[2..3] }` -> `{ kind:"compare", products: Product[], rows: [{label, values:(string|null)[]}], verdict: string }`.
3. `check_compatibility` [UI] input `{ product_id: string, device?: string }` -> `{ kind:"compat", product, device, status:"confirmed"|"family_only"|"not_listed"|"incompatible", evidence:{ source:"tags"|"title"|"description"|"options", quote:string }|null, note: string, alternatives: Product[], also?: [{device, status, evidence}] }`. `confirmed` only when the store names this exact model, with a literal quote from the store data (a tag counts only when the tag is the device itself, not a label like "magsafe charger"); spelling variants ("iphone17 pro") are normalized. `family_only` (v1.6) when the store names only the series or family: "iPhone 17" for an iPhone 17 Pro, "MacBook Pro" for a MacBook Pro 2017 Intel or a MacBook Pro 14 M3, "MacBook Air" for a MacBook Air M3. The quote is the series the store lists and the spoken text says so ("The store lists iPhone 17, not your iPhone 17 Pro specifically."); it is never a yes. `incompatible` only from the store's own negation ("Not compatible with Saros 10R", quoted) or a hard connector rule (Lightning vs USB-C), with the title as evidence. A named model in `device` always wins over the closet. Without `device`, all closet devices are checked: the first is the main answer, the rest go to `also`, and `device_source: "closet"` (else `"said"`); the spoken text then names the shopper's device ("The store lists your iPhone 15 for the OntheGo 67W Slim Wall Charger."). A kind word in `device` ("my phone", "my laptop", "my robot", "my computer") picks the closet devices of that kind: one -> it is used; several -> error `device_ambiguous` with `options` (the shopper is asked which one, nothing is picked silently); none -> `device_required`. `device` in the answer is the full device as the shopper named it ("MacBook Pro 2017 Intel"). Any answer other than confirmed speaks the first listed alternative; an `incompatible` from the store's own negation quotes it. A free-text device that starts with the store's brand ("Roborock Q7 M5" at Roborock) is matched without the brand. A free-text device (outside the device dictionary, e.g. every Roborock robot) is matched by meaning, not by substring (v1.7.1): the name must end where the model ends ("for Qrevo Curv" is not a listing for a Qrevo, "S8 Pro Ultra" not for an S8, "Saros 10 R" not for a Saros 10; "X only" and "QRevo 1 Year" do list X); a predecessor or comparison ("Upgraded from S8 MaxV Ultra", "replaces", "vs", "compared to", "than") is not a listing; a product that is itself a device (a robot, a vacuum) is `not_listed` for any device, its own model included; the store's series or "+" edition for another model in it ("Saros Series" for a Saros 10, "Q7 Max+" for a Q7 Max) is `family_only` with that name as the quote, while a series named after the exact model ("Qrevo Curv Series" for a Qrevo Curv) is `confirmed`; "Incompatible with other models in the Qrevo series" is `incompatible` for a Qrevo S and never for the Qrevo itself.
4. `remember_my_devices` [UI] input `{ devices?: string[], home?: { pets?: string[], notes?: string } , forget?: string[] }` -> `{ kind:"closet", devices: string[], items: [{ name, kind }], home, store: string, suggestion: { device, product: Product, evidence:{source, quote} } | null }`. `suggestion` is one proactive tip: the cheapest in-stock accessory THIS store lists for a remembered device (newest device first), with the store's quote; never a robot/vacuum, protection plan, trade-in or points item, never something already ordered here; null when nothing is listed or the catalog is unreachable. Only when devices were added.
Each device is kept as the shopper named it ("MacBook Pro 2017 Intel"; "iphone 17 pro" is stored with the model's own spelling, "iPhone 17 Pro"); parsing is used only for matching, `forget` matches the same way. `items` (v1.6) repeats `devices` with a `kind` for the icon: `phone`, `laptop`, `tablet`, `desktop`, `watch`, `earbuds`, `robot`, `other`.
5. `my_devices` [UI] input `{}` -> same shape as 4 (with `suggestion`). The spoken text names the devices (and the tip) only; pets and home notes stay on the screen.
6. `prepare_order` [UI] input `{ items: [{ id, qty }] }` -> `{ kind:"order_preview", items:[{product, qty, line_total}], subtotal, shipping: number|null, total, currency, confirmation_token, expires_at }`. `shipping` is null when the store policy is unknown (both demo stores): the total is then "before shipping and tax". Unavailable items are refused with a reason. Token = HMAC over user+items+total, 10 min.
7. `place_order` [UI] input `{ confirmation_token }` -> `{ kind:"order", order:{ id, status:"confirmed", created_at, eta, items, subtotal, shipping, total, currency, payment:"simulated (Amazon Wallet style)", store }, already_placed?: true }`. Bad/expired token -> error text, nothing placed. Replaying a used token returns the same order with `already_placed: true` (no second order). Stock and total are re-checked at placement.
8. `order_status` [UI] input `{ order_id?: string }` -> `{ kind:"orders", orders:[order] }` (latest first). Works in a new session for the same signed shopper. `eta` is the store config's demo estimate and is said and shown as such.
9. `talk_to_staff` input `{ reason: string, contact?: string }` -> `{ kind:"handoff", ticket_id, message }`. Notifies the store owner (Telegram if configured, else log).

## Errors
Tool errors return `isError: true` with a spoken-friendly `text` and `structuredContent: { kind:"error", code, message }`. Never throw raw stack traces.

Codes: `not_found`, `out_of_stock`, `invalid_input`, `device_required`, `device_ambiguous` (v1.6, carries `options: string[]`, the remembered devices to choose from), `anonymous` (no session: no closet, no orders), `token_invalid`, `token_expired`, `token_wrong_user`, `price_changed`, `catalog_unavailable`, `internal`.
